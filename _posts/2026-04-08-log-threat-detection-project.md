# 로그 기반 위협 탐지 및 대응 자동화 시스템

## 프로젝트 개요

이번 프로젝트는 다양한 형식의 보안 로그를 읽고, 이를 공통된 이벤트 형태로 정리한 뒤 위협을 탐지하고 대응까지 연결하는 시스템을 구현하는 것을 목표로 함

단순히 로그를 화면에 출력하거나 문자열을 검색하는 것이 아니라  
로그 파싱, 이벤트 정규화, 탐지 룰 적용, 인시던트 생성, 대응 이력 저장까지 이어지는 흐름을 다룸

즉, 보안관제나 침해사고 대응에서 사용하는 기본적인 흐름을 작은 규모로 직접 구현해보는 프로젝트


## 프로젝트를 선택한 이유

보안 운영 환경에서는 많은 로그가 계속 생성됨

하지만 사람이 모든 로그를 직접 확인하고 위협 여부를 판단하기에는 한계가 있음

그래서 로그를 일정한 기준으로 정리하고,  
위협으로 볼 수 있는 조건을 탐지 규칙으로 만들어 자동으로 분석하는 구조가 필요하다고 생각함

이 프로젝트를 통해 배우고 싶은 부분은 단순 Python 문법이 아니라  
로그 분석이 실제 보안 대응 흐름과 어떻게 연결되는지 이해하는 것

특히 아래 흐름을 직접 만들어보는 것이 목표

```text
로그 수집 → 파싱 → 정규화 → 탐지 → 인시던트 생성 → 대응 → 기록 저장
```


## 프로젝트 목표

이 프로젝트의 목표는 여러 형식의 로그를 하나의 기준으로 정리하고,  
그 안에서 보안 위협을 자동으로 탐지한 뒤 대응까지 연결하는 구조를 구현하는 것

탐지하고 싶은 주요 시나리오

- 브루트포스 공격
- 로그인 실패 후 성공으로 이어지는 계정 탈취 의심 행위
- 인코딩된 PowerShell 실행
- Mimikatz 같은 수상한 명령 실행
- 관리자 권한 부여나 역할 변경 같은 권한 상승
- 대량 다운로드나 전송에 따른 데이터 유출
- 여러 호스트 간 이동에 따른 측면 이동
- 피싱 관련 이메일 이벤트
- 로그 삭제나 감사 중지 같은 로그 변조 및 흔적 제거


## 전체 동작 흐름

프로젝트의 전체 흐름은 다음과 같음

1. 입력 로그 파일 읽기
2. 로그를 파싱해 공통 이벤트 구조로 변환
3. 탐지 엔진이 여러 탐지 룰에 이벤트 적용
4. 조건이 맞는 경우 인시던트 생성
5. 대응 계획에 따라 차단, 격리, 알림 등을 수행
6. 인시던트와 대응 결과, 룰 상태 저장

이 흐름에서 가장 중요하게 봐야 할 부분은  
로그를 단순 문자열로 보지 않고, 분석 가능한 이벤트 구조로 바꾸는 과정이라고 생각함


## 프로젝트 구조

현재 생각한 프로젝트 구조는 다음과 같음

```text
project/
├── parser.py
├── models.py
├── rules.py
├── engine.py
├── responders.py
├── config.py
├── cli.py
├── samples/
├── state/
└── tests/
```

각 파일의 역할

- `parser.py`: 로그를 읽고 이벤트로 변환
- `models.py`: Event, Incident 등 공통 데이터 구조 정의
- `rules.py`: 탐지 규칙 구현
- `engine.py`: 전체 탐지 흐름 제어
- `responders.py`: 대응 조치 수행
- `config.py`: 설정값 관리
- `cli.py`: 명령줄 실행 인터페이스
- `samples/`: 샘플 로그와 설정 파일
- `state/`: 실행 결과 및 상태 저장
- `tests/`: 기능 검증용 테스트 코드


## 주요 구성 요소

### 로그 파싱 및 정규화

로그는 시스템마다 형식이 다를 수 있음

예를 들어 JSON 형식의 로그도 있을 수 있고,  
`key=value` 형식의 로그도 있을 수 있음

따라서 서로 다른 로그를 그대로 탐지 규칙에 적용하면 구조가 복잡해질 수 있음

그래서 먼저 로그를 공통된 이벤트 구조로 변환하는 과정이 필요함

이 과정을 정규화라고 볼 수 있음

정규화가 되어야 이후 탐지 규칙을 일관되게 적용할 수 있음


### 탐지 엔진과 상태 기반 룰

탐지 엔진은 정규화된 이벤트를 여러 탐지 룰에 적용하는 역할을 함

단순한 탐지는 한 줄의 로그만 보고 판단할 수 있음

하지만 실제 공격 흐름은 여러 이벤트가 시간 순서대로 이어지는 경우가 많음

예를 들어 브루트포스 공격은 로그인 실패가 한 번 발생했다고 바로 공격이라고 판단하기 어려움

하지만 짧은 시간 안에 같은 IP나 같은 계정으로 로그인 실패가 반복되면 공격 가능성이 높아짐

그래서 상태 기반 탐지가 필요함

상태 기반 탐지는 단일 이벤트만 보는 것이 아니라  
시간 흐름과 누적 상태를 함께 보는 방식

이 부분이 단순 문자열 검색과 가장 큰 차이점이라고 생각함


### 인시던트 생성

탐지 조건에 맞는 이벤트가 발생하면 인시던트를 생성함

인시던트는 단순 탐지 결과가 아니라  
보안적으로 확인해야 할 사건 단위라고 볼 수 있음

인시던트에는 아래 정보가 포함될 수 있음

- 탐지된 위협 유형
- 관련 사용자
- 관련 IP
- 관련 호스트
- 탐지 근거
- 심각도
- 발생 시간
- 대응 계획

이렇게 남겨야 나중에 어떤 이유로 탐지되었는지 확인할 수 있음


### 대응 자동화

탐지에서 끝나지 않고 대응까지 연결하는 것이 이 프로젝트의 중요한 특징

대응 예시

- IP 차단
- 사용자 격리
- 계정 비활성화
- 호스트 격리
- 알람 전송
- 대응 이력 저장

처음부터 실제 방화벽이나 외부 시스템과 연결하는 것은 위험할 수 있음

그래서 먼저 `dry-run` 모드로 탐지 결과와 대응 계획만 확인하고,  
이후 `live-response` 모드에서 실제 상태 파일에 대응 결과를 반영하는 방식으로 구성할 수 있음


## 대응 모드

### dry-run

`dry-run` 모드는 실제 차단이나 격리를 수행하지 않음

탐지 결과와 대응 계획만 확인하는 방식

오탐 여부를 확인하거나 탐지 규칙을 테스트할 때 적합함


### live-response

`live-response` 모드는 차단, 격리, 비활성화 등의 대응을 실제로 반영함

실행 결과는 상태 파일에 저장됨

동일 대상에 대한 중복 대응을 방지하거나,  
쿨다운 시간을 적용하는 구조도 함께 고려할 수 있음


## 출력 파일

실행 결과는 `state` 디렉터리에 저장하는 구조로 설계함

```text
state/
├── incidents.jsonl
├── response_history.jsonl
├── blocked_ips.json
├── quarantined_users.json
├── disabled_users.json
├── isolated_hosts.json
└── rule_state/
```

각 파일의 역할

- `incidents.jsonl`: 탐지된 인시던트 기록
- `response_history.jsonl`: 대응 이력
- `blocked_ips.json`: 차단된 IP 목록
- `quarantined_users.json`: 격리된 사용자 목록
- `disabled_users.json`: 비활성화된 계정 목록
- `isolated_hosts.json`: 격리된 호스트 목록
- `rule_state/`: 상태 기반 룰의 누적 상태 저장

탐지 결과를 단순히 화면 출력으로 끝내지 않고,  
다음 실행에도 활용할 수 있도록 저장하는 것이 중요함


## 샘플 로그 시나리오

샘플 로그는 각 탐지 규칙을 테스트하기 위한 데모 데이터 역할을 함

예시 시나리오

- `alice`: 여러 번 로그인 실패 후 성공
- `bob`: 인코딩된 PowerShell 실행
- `administrator`: 권한 상승 관련 이벤트
- `carol`: 대량 다운로드 또는 전송
- `mallory`: 보안 로그 삭제 명령 실행
- `ops-temp`: 여러 서버 이동 로그인
- 이메일 관련 이벤트: 피싱 탐지 예시

샘플 로그를 통해 각 탐지 룰이 실제로 어떤 조건에서 동작하는지 확인할 수 있음


## 설정값 관리

설정 파일에서는 탐지 룰의 활성화 여부와 임계값을 조정할 수 있음

설정 가능한 항목 예시

- 브루트포스 실패 횟수
- 시간 창(window)
- 수상한 명령 키워드
- 데이터 유출 기준값
- 예외 사용자
- 예외 호스트
- 예외 IP
- ChatOps 알림 사용 여부
- 방화벽 API 연동 여부

설정값을 코드에 직접 넣지 않고 분리하면  
탐지 기준을 상황에 맞게 조정하기 쉬움


## 테스트

이 프로젝트에서는 탐지 기능이 실제로 동작하는지 확인하기 위한 테스트도 필요함

테스트할 부분

- 브루트포스 탐지
- 계정 탈취 의심 시나리오
- 측면 이동 탐지
- 실제 대응 모드에서 상태 파일 생성
- 중복 대응 방지
- 예외 사용자 처리
- 파서 오류 처리

테스트가 있어야 단순히 구조만 존재하는 프로젝트가 아니라  
핵심 기능이 실제로 동작하는지 확인할 수 있음

이번 프로젝트에서 특히 중요하게 공부할 부분은 다음과 같음

보안 이벤트를 어떤 기준으로 해석하고 판단할 것인지가 중요해 보임


## 한계점

이 프로젝트는 파일 기반 로그 처리 방식이기 때문에  
실제 운영 환경처럼 대규모 로그를 실시간 처리하는 구조는 아님

또한 규칙 기반 탐지 중심이라  
새로운 공격 패턴을 학습 기반으로 찾아내는 기능은 포함되어 있지 않음

CLI 중심 구조이기 때문에 대시보드나 시각화 화면은 아직 없음

외부 연동도 기본적으로는 비활성화 상태로 두는 것이 안전해 보임


## 개선 방향

앞으로 개선하고 싶은 방향

- 실시간 로그 수집 구조 추가
- 이상행위 탐지 또는 위험 점수화 기능 추가
- 대시보드 또는 웹 UI 구성
- Slack, Teams 알림 연동
- 방화벽 API 연동
- 보고서 자동 생성 기능 추가
- 탐지 룰별 설명 문서 작성
- MITRE ATT&CK 기법과 연결해서 정리


## 배운 점

이번 프로젝트를 통해 보안 탐지가 단순히 수상한 문자열을 찾는 작업이 아니라는 점을 이해하게 됨

서로 다른 형식의 로그를 공통 기준으로 정리해야 하고,  
개별 이벤트만 보는 것이 아니라 시간 흐름과 누적 상태를 함께 봐야 더 의미 있는 탐지가 가능함

또한 보안 업무는 탐지에서 끝나는 것이 아니라  
차단, 격리, 알람, 기록 저장까지 이어지는 전체 흐름을 함께 봐야 한다는 점을 알 수 있었음

아직은 작은 규모의 프로젝트지만,  
보안관제와 침해사고 대응의 기본 흐름을 직접 구현해볼 수 있다는 점에서 의미가 있다고 생각함
